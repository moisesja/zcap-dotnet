# Issue #148 — `CompositeDidResolver` drops method-specific verification relationship resolution

Scope approved by the user: all items below. Branch: `148-composite-relationship-resolver`.
An independent design critique ran on the plan before approval; its accepted findings are
folded in (split fail-closed codes, root-resolver test trap, ablation targets, two extra
cases, no constructor log, trailing-colon documentation only).

## Human intent and decisions

- Make `CompositeDidResolver` implement `IVerificationRelationshipResolver` and route
  controller-purpose checks to the registered method adapter, keyed on the controller DID
  (forwarded verbatim), never on the verification method's DID.
- Fail closed with a tri-state result, never an exception, so the multi-controller loop
  continues. Unroutable controller ⇒ `methodNotSupported` (Debug, attacker-drivable).
  Matched adapter that resolves keys only ⇒ `internalError` (Warning, operator
  misconfiguration). Never infer authority from successful key resolution.
- Keep `VerificationService` precedence unchanged: explicit `relationshipResolver` >
  self-providing `didResolver` > built-in did:key default. Document and test it. No DI
  wiring change; `AddZcapDidResolver(composite)` alone now suffices.
- One diagnosability change: the controller-not-resolvable log also emits the resolver's
  message. No constructor-time selection log.
- Prefix matching unchanged; document full prefixes with the trailing `:`.
- `docs/IMPLEMENTATION-COMPLETE.md` stays untouched: it is a frozen historical report.

## Results

- Ablation A (composite no longer implements the interface, full test-project rebuild):
  **7/25** composite tests fail — owner invocation, cross-DID reference, both valid chains,
  key-only Warning, unregistered-method message, revocation. Restored.
- Ablation B (key-only adapter infers authority from successful key resolution): **2/25** Core

## Adversarial review (independent agent, 23 executed probes)

No authorization bypass found: loose/catch-all/overlapping registrations, controller-string
manipulation (fragment, query, path, case, homoglyph, NUL, newline, 100k chars), cross-DID
routing, revocation and explicit precedence all behaved as designed. Dispositions:

- F1 (LOW, confirmed) a throwing child adapter aborted the multi-controller loop as
  `CouldNotVerify`, locking out a co-controller of another method. **Fixed**: the composite maps
  adapter exceptions (not cancellation) to `internalError`; the verifier logs Warning and
  continues. Regression tests: unit mapping, cancellation propagation, `[did:web down, did:key]`
  still `Valid`, single faulting controller ⇒ `UnauthorizedController`.
- F2 (LOW, confirmed) with a key-only adapter registered AND a legitimate delegation to a controller
  of that method, anyone can repeat the Warning. **Accepted**: both preconditions are deployment
  facts, the Warning is the signal to fix the configuration, and a dedupe cache would add state to
  the verifier. Documented in the composite remarks.
- F3 (LOW, confirmed) DI key-only test was a false green. **Fixed**: asserts the Warning with
  `internalError` through a logger registered in the container. Also added the missing
  "adapter was consulted" assertion to the multi-controller test.
- F4 (LOW, confirmed, pre-existing) key path threw `InvalidOperationException` for an unregistered
  method ⇒ Warning + `CouldNotVerify`, drivable anonymously via the proof `verificationMethod`.
  **Fixed**: throws `CapabilityValidationException` (Debug), matching `DidKeyResolver`; test added.
- F5/F6 (INFO) explicit-resolver shadowing and catch-all-first registrations are operator footguns.
  **Documented** (XML docs, README); no constructor log per the Simplicity First decision.

Post-review verification: full solution **485 Core + 11 ASP.NET passed** on the committed package
versions; no warning from changed files. Ablation C (adapter exceptions propagate again): **3/30**
composite tests fail. Ablation D (key path throws `InvalidOperationException` again): **2/30** fail.
Source restored and re-verified green. A working-tree edit bumping `NetCrypto` 1.6.0→1.7.1
and `DataProofsDotnet.Legacy` 1.1.1→1.3.0 in `ZcapLd.Core.csproj` appeared during the session and was
kept out of the #148 commits until the user confirmed it was theirs.
