# Issue #99 — Delegation-proof `created` freshness/consistency check

Branch: `99-delegation-proof-created-check`

## Problem
`VerifySingleDelegationProofAsync` checked `capability.expires` but never inspected the delegation
`proof.created`, so a delegation proof could claim any `created` (future-dated, etc.) and still verify.
Follow-up to #71 (which added `created` freshness to the invocation/revocation paths). Severity: LOW
(security hardening; not a spec MUST; `expires` already bounds outer validity).

## Decisions (evaluated via workflow + confirmed with user)
- **Scope**: ship the two checks that catch something real — future-dated (always on) + unparseable
  (always on) + missing (opt-in). **Dropped** the issue's `created <= expires` rule: it is redundant
  (every `created > expires` case is already caught by the existing `Expired` check or the future-dated
  check) and false-reject-prone at the clock-skew boundary. **Deferred** parent/child window consistency.
- **No staleness lower-bound** (the #71↔#99 distinction): a durable delegation signed months ago must
  verify until it `expires`. Do NOT reuse `GetFreshProofCreatedUtc`.
- **Missing `created`**: opt-in via `VerificationPolicy.RequireDelegationProofCreated` (default false) —
  pre-existing/cross-stack delegations may legitimately omit it.
- **Revocation path**: skip the check (`applyCreatedCheck: false`) so a malformed-`created` delegation
  stays revocable, mirroring the #73 ceiling carve-out.
