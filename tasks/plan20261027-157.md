  `{ "type": …, …params }` entries. Consumers "will extend it, just like before": they subclass

  EpsilonBudget lives in examples/tests, not Core.

  latest published versions.

## Design summary

- Each registered caveat type gets a library-generated, pinned, never-fetched JSON-LD context
  `urn:zcap-dotnet:caveat-context:v1:<Type>` defining the type IRI and every parameter as `@json`,
  so the type and full parameter values are signed. Undeclared params/types (which RDFC would
  drop) are rejected — the #149 defect class.
- Integrity rules: closed key sets, own-`@context` requirement, literal bounds, JCS-canonical
  numbers in a JCS-equal domain, no `null`, no aliases/keywords/`:` keys under the profile.
- `Caveat` carries schema/attenuation only (no `IsSatisfied`); resource-owned `ICaveatHandler`s
  enforce at invocation after signature, authorization and replay. Chain/proof APIs return
  `CaveatEnforcementRequired` for caveat-bearing chains; only invocation authorizes.
- Default profile unchanged.

### Adversarial review (two independent agents) and dispositions

Authorization/enforcement review:
- F1 HIGH (fixed, 3f25895): the handler contract advised idempotency by `InvocationId` and the
  reference ledger/example cached decisions by it; an invoker could reuse an approved id after the
  nonce window with a costlier action. Advice and caches removed; nonce/ledger sharing documented.
- F2 MEDIUM (fixed): handler `TaskCanceledException` skipped `ReleaseAsync`. All exceptions now
  release (no caller token exists on this path).
- F3 LOW (fixed): standalone proof check of a deep link returned Valid while its unverified
  embedded parent hid a caveat; with a registry such links report `CaveatEnforcementRequired`.
- Suspected (addressed by docs/limits): envelope action/target not pinned by the relying party
  (documented: resource must perform exactly the signed action/target; DI form pins them);
  large chains hitting NetCid's 1 MB JCS default (comparison limit raised, 64 KiB caveat cap).

Signature/canonicalization review:
- HIGH (fixed, 6b2d905): dotNetRDF silently drops IRIs .NET deems malformed. Bracketed invocation
  targets (`?filter[id]=123`) were unsigned and rewritable under target attenuation; a malformed
  capability id unsigned the whole node (controller/actions/caveats editable, fresh ids after
  revocation); malformed invocation ids allowed replay. Ids, parentCapability, targets,
  controllers and (730cd95) verificationMethod must now be well-formed, at signing and verify.
- LOW (fixed): caveat type names equal to context terms are refused at registration.
Verification pass on the dropped-IRI fixes (third agent):
- CONFIRMED (fixed): `AbsoluteUri` is not the form dotNetRDF signs. Percent-encoded dot segments
  in targets (`/public/%2E%2E/admin`) signed outside the delegated path under target attenuation,
  and http(s) ids with an invisible trailing segment (`…/7/%C2%AD`) signed as `…/7/`, evading
  revocation and replay. Ids and targets are now accepted only when canonicalizing the IRI itself
  returns it unchanged (cached); a bare-authority target may gain its root `/`.
- LOW (documented): the revocation `proofPurpose` is not a defined suite term, so it is unsigned;
  the signed `revoke` action and single-purpose paths prevent cross-purpose use.
- Suspected (left as is): outside the caveat profile the envelope path matches the embedded and
  supplied capability by id only (pre-existing; the supplied chain carries the authority).

- Pre-existing, out of scope (follow-ups to raise): the ecdsa-2019/v1 context is served by
  neither loader, so P-256 RDFC verification always falls back to DataProofs' JCS variant; and
  DataProofs' `RdfcDocumentCanonicalizer` could run dotNetRDF in safe mode / fail on parser
  warnings so dropped IRIs and terms fail closed for every consumer (dataproofs-dotnet change).
