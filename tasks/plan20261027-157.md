## Human intents and decisions

  implementation". JS compatibility is not an acceptance requirement for caveat-bearing zcaps;
  caveat-free zcaps must stay default-profile compatible.

  `{ "type": …, …params }` entries. Consumers "will extend it, just like before": they subclass

  EpsilonBudget lives in examples/tests, not Core.
- Update NetCrypto (crypto-dotnet), DataProofs (dataproofs-dotnet) and NetCid (net-cid) to the
  latest published versions.
- Approved plan: `~/.claude/plans/quirky-nibbling-goblet.md` (mirrored below).

## Design summary

- Each registered caveat type gets a library-generated, pinned, never-fetched JSON-LD context
  `urn:zcap-dotnet:caveat-context:v1:<Type>` defining the type IRI and every parameter as `@json`,
  so the type and full parameter values are signed. Undeclared params/types (which RDFC would
  drop) are rejected — the #149 defect class.
- Integrity rules: closed key sets, own-`@context` requirement, literal bounds, JCS-canonical
  numbers in a JCS-equal domain, no `null`, no aliases/keywords/`:` keys under the profile.
- `Caveat` carries schema/attenuation only (no `IsSatisfied`); resource-owned `ICaveatHandler`s
  enforce at invocation after signature, authorization and replay. Chain/proof APIs return
  `CaveatEnforcementRequired` for caveat-bearing chains; only invocation authorizes.
- Default profile unchanged.
