# Issue #155 — revocation endpoint decodes the capability id twice

## Intent

The user asked to assess whether GitHub issue #155 is a real defect and, if so, to fix it.
Verdict: **real**. `MapZcapRevocationEndpoints` binds `{*capabilityId}` (already decoded once by
ASP.NET Core, except `%2F`) and calls `Uri.UnescapeDataString` on it again. Every root id
(`urn:zcap:root:` + `encodeURIComponent(target)`) therefore reads as a different id: `GET` reports a
revoked root as not revoked and `POST` cannot revoke a root (route/body mismatch → 400).

## Facts established by probing both hosts (scratch test, removed afterwards)

- Kestrel and TestServer both hand the handler a route value decoded once, except `%2F`, which stays
  encoded. Root ids arrive as the true id; ids containing `/` arrive as `https:%2F%2F…`.
- Kestrel populates `IHttpRequestFeature.RawTarget` (origin form, query included, `PathBase` kept).
  **TestServer leaves it empty.** The route value alone cannot distinguish a literal `%2F` (raw
  `%252F`) from an encoded `/` (raw `%2F`), so only the raw target identifies the id exactly.
- `PathString.FromUriComponent(string)` decodes exactly like the servers do (every escape except
  `%2F`), which gives a cheap consistency check between a raw suffix and the routed value.
- `Microsoft.AspNetCore.Mvc.Testing` 10.0.13 exposes `WebApplicationFactory.UseKestrel()`, so the
  demo host can be exercised on real Kestrel from the existing test project.

## Decisions

- Recover the id from `RawTarget` when the server exposes it: strip the query, take the suffix of the
  raw path that holds exactly as many `/` as the route value (counting back from the end, so
  `PathBase`, the prefix's encoding and absolute-form targets never need parsing), require that
  suffix to decode (except `%2F`) to the route value, then `Uri.UnescapeDataString` it once.
  A mismatch (server normalized the path) fails closed with 400.
- When `RawTarget` is empty (TestServer), use the route value verbatim: exact for every id without
  an encoded `/`, which includes all root and `urn:uuid` ids. Document that limitation.
- Keep the `{prefix}/{encodeURIComponent(id)}` convention; `Uri.EscapeDataString` output decodes
  identically.
- Out of scope: the null-valued fields on the anonymous `GET` response (the issue's separate low
  observation). Noted for a follow-up, not changed here.

## Results

Verdict: issue #155 is real and is fixed on this branch (uncommitted).

Additional security finding, fixed in the same change: enabling root revocation over HTTP exposed a
pre-existing Core gap. `RevokeCapabilityAsync(Capability, Invocation)` trusted a body-supplied root:
a root-only chain has no delegation proof, so a body carrying a known root id with the caller's own
`controller` was authorized against that controller and the victim root was revoked. (On `main` this
was reachable over HTTP with a triple-encoded URL.) The adversarial reviewer then showed the first
anchoring attempt, keyed on the request's `parentCapability`, could be bypassed by presenting the
victim root's id as a delegated-shaped capability under the attacker's own valid chain. Final rule in
`IsRevokerAuthorizedAsync`: whether an id is a root is decided by the verifier's trust store (explicit
root or `IRootCapabilityResolver`); a known root id is anchored to the trusted root however the request
shapes it; a root-shaped or `urn:zcap:root:`-named id the verifier cannot resolve fails closed.

Known limitations, documented in architecture.md and left for follow-up:
- Delegated ids are self-asserted and revocation records are keyed by id, so a delegator can mint a
  capability bearing a sibling's delegated id under its own chain and revoke that id. Closing this
  needs root-scoped (or digest-bound) revocation records: a store/interface change.
- The anonymous `GET` still serializes the unused record fields as `null` (the issue's separate low
  observation); not changed here.
- Without a raw target (TestServer) an id containing an encoded `/` stays `%2F`; absolute-form request
  targets with an encoded `/` in the id fail closed (400); a proxy that re-encodes the path breaks
  ids containing escapes.

Validation:
- New tests fail on the unfixed code: 14 endpoint cases (both hosts) and 3 of 4 initial Core cases.
- `dotnet test ZcapLd.sln`: ZcapLd.AspNetCore.Tests 32 passed, ZcapLd.Core.Tests 496 passed.
- Adversarial agent: no remaining confusion or collision on Kestrel across `%2F`/`%2f`/`%25`/raw `/`/
  dot segments/query/`#`/invalid UTF-8/PathBase containing the prefix/long inputs; the delegated-shaped
  root forgery (F1) it found is fixed and pinned by tests in both suites; its `%00` 500 (F3) is now a 400.
