# Issue #159: P-256 (EcdsaSecp256r1Signature2019) cannot sign or RDFC-verify

Branch: `159-p256-ecdsa-2019-context`, created from `origin/main` @ 3da1412.

## Context

`ZcapSuiteCatalog` advertises `EcdsaSecp256r1Signature2019` with the context
`https://w3id.org/security/suites/ecdsa-2019/v1`. Neither `RdfcContextDocumentLoader` nor
DataProofs' `OfflineDocumentLoader` serves it, and the canonicalizer fails closed, so every P-256
delegation, invocation and revocation fails with "could not be RDFC-canonicalized". No test signs a
P-256 capability end to end; `InMemoryDidProvider` (test helper) is Ed25519-only.

The issue is confirmed, and its premise is weaker than stated: the URL is **not a published
context at all**. `https://w3id.org/security/suites/ecdsa-2019/v1` returns 404. It comes from the
2022 W3C CG final report "ECDSA Cryptosuite v2019" (examples only; superseded by
`DataIntegrityProof` / `ecdsa-rdfc-2019` under `data-integrity/v2`). DataProofs' own suite docs say
"No context is published for EcdsaSecp256r1Signature2019, so supply one that defines its terms".

Grounding (lesson 2026-10-29): the ZCAP spec is suite-neutral and only requires a delegated
`@context` array beginning with zcap/v1. `@digitalbazaar/zcap` has no P-256 legacy suite at all.
The published contexts that define the type are `https://w3id.org/security/v2` (flat, unprotected,
`jsonld-signatures`' `SECURITY_CONTEXT_URL` for 2018/2019-era suites, with `sec:`/`dc:`/`xsd:`
prefixes) and, type-scoped, the VC 1.1 context `https://www.w3.org/2018/credentials/v1`.

Probe (scratchpad, real DataProofs 1.5.0 canonicalizer): a P-256 delegated capability, delegation
proof options, envelope invocation proof, revocation proof and DI application document canonicalize
successfully under zcap/v1 plus **any** of: security/v2, credentials/v1, a locally authored
type-scoped context modelled on ed25519-2020/v1. All produce **byte-identical N-Quads** (the
`@context` is not a triple; only the term definitions matter, and those are identical). No
protected-term redefinition error for zcap/v1 + security/v2 in dotNetRDF.

## Decisions (made in an autonomous session; each is cheap to flip because the signed bytes do not change)

1. **Suite context: a zcap-dotnet-local, `@protected`, type-scoped context**
   `urn:zcap-dotnet:ecdsa-secp256r1-2019-context:v1`, the ed25519-2020/v1 shape with the
   suite/key type names swapped. Reasons: P-256 is already a zcap-dotnet-only profile (base58-btc
   `proofValue` over IEEE P1363, no peer stack); the repo marks non-interoperable profiles with
   `urn:zcap-dotnet:` contexts (#157 caveat contexts, revocation context); it adds no prefixes and no
   vocabulary beyond the suite's own terms to the trusted context set; it does not squat a w3id URL
   whose public meaning could later diverge from the embedded bytes.
   Alternative kept on record: `https://w3id.org/security/v2` (published; same bytes; brings ~150
   unprotected terms and three prefixes into the trusted set and into the caveat reserved names).
   Rejected: keeping the 404 URL with private bytes; `credentials/v1` (a VC context on a zcap).
2. **JCS-variant fallback: off.** `LegacyProofCrypto` constructs the DataProofs suites with
   `LegacyVariantVerification.ConstructedVariantOnly`, so only RDFC-1.0 proofs verify. This is what
   README ("RDFC-1.0 only") and the 4.0.0 changelog ("JCS-signed capabilities do not verify") already
   promise, and what the JS reference does. A test pins the rejection for both suites.
3. **Caveat reserved terms** come from `ZcapSuiteCatalog` (zcap/v1 plus every supported suite
   context). The silent `continue` on an unservable context is removed: a supported context that the
   loader cannot serve is a build defect and throws.
4. **Stop advertising the 404 URL.** `IsSupportedContext("…/ecdsa-2019/v1")` is false; a capability
   carrying it is rejected by the profile (`MalformedCapability`).
