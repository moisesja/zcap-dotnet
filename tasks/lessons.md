## 2026-04-29 06:51 — Cross-stack signing payload bugs are invisible to in-process round-trip tests
- For any cryptographic canonicalization / signing path, sign↔verify round-trip tests in the same library are necessary but **not sufficient**: a structurally wrong-but-self-consistent payload passes them. The only test that catches drift is a **known-answer fixture** that pins canonical bytes (or their SHA-256) to a value computed independently — ideally generated by a peer implementation.
- W3C Verifiable Credentials Data Integrity signs a **flat** payload: document's own top-level fields plus a `proof` field whose value is the on-document proof minus `proofValue`. **No wrapper.** Any `{ document: {...}, proof: {...} }` shape is a bug regardless of how clean the round-trip looks.
- When copying a proof object into a signing payload, **copy minus the excluded field** (`proofValue`); never hand-pick a whitelist. Future proof fields (nonce, domain, id, challenge) will be added and a whitelist silently drops them — re-introducing the same drift you fixed.
- DateTime fractional-second precision is a parallel cross-stack interop hazard: .NET's default emits 7-digit (100-ns tick) precision; Python / JS / Rust emit 6-digit (microsecond). Pin the on-wire format with a `JsonConverter` (`yyyy-MM-ddTHH:mm:ss.ffffffZ`) on every model property whose value goes through JCS — `Proof.Created`, `Capability.Expires`, etc.

## 2026-04-29 09:40 — Round-tripping through a typed model is the wrong intermediate for canonicalization
- "Copy the proof verbatim minus `proofValue`" doesn't survive a model round-trip. Any `[JsonConverter]` reformatting (e.g. an Iso-microsecond DateTime converter) silently rewrites the canonicalization input — every other Data Integrity verifier JCS-canonicalizes the on-wire timestamp **as an opaque string**, so any reformatting at the canonicalization boundary diverges the bytes the signer signed from the bytes we hash.
- Likewise, anything not declared on the typed model is dropped on serialize. `domain`, `nonce`, `id`, `challenge`, custom proof extensions — all silently lost. Add `[JsonExtensionData] Dictionary<string, JsonElement>?` on every model that crosses a canonicalization boundary, even if you don't use those fields today.
- For timestamp-shaped fields that participate in canonicalization, store them as **`string`** on the model and expose a parsed `DateTime` accessor via `[JsonIgnore]`. The string is byte-stable across deserialize/serialize; the DateTime is just a convenience view. Inverting that — `DateTime` with a converter — is what bug #36 was.
- `Utf8JsonWriter`'s default encoder is `JavaScriptEncoder.Default`, which escapes `+`, `<`, `>`, `&`, `'` for HTML safety. RFC 8785 §3.2.2.2 mandates only `"`, `\`, and control chars are escaped. Use `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` for any `Utf8JsonWriter` whose output is hashed — the HTML-safe defaults will diverge from any RFC 8785-conformant peer.
- Verifier round-trip tests pass even when the verifier reformats — the verifier's reformat matches the signer's reformat. Test against **wire bytes**: deserialize from a frozen JSON string fixture, canonicalize, assert the canonical bytes contain the on-wire substring verbatim.

## 2026-06-03 — The plan-gate lesson RECURRED; and severity in fail-closed logging
- **Recurrence (same mistake as 2026-06-02):** I again jumped into editing for a multi-finding review without entering plan mode / requesting approval. The user stopped me: "follow AGENTS.md... you skipped giving me a plan for approval." The prior lesson existed and I still missed the gate. **Reinforced rule:** "address these N findings" — even when the findings come with concrete, spelled-out fixes — is a hard `EnterPlanMode` → plan file → `ExitPlanMode` trigger. An explicit fix list is NOT a substitute for sign-off; if anything it makes skipping the gate more tempting. Read-only investigation first is correct and encouraged; mutations wait for approval.
- **Fail-closed logging needs a severity policy, not blanket Warning.** When you widen a `catch` to log the cause (good for observability), classify by exception type: attacker-drivable validation/parse failures (malformed input, unsupported/unresolvable proof, bad multibase) → **Debug**; genuinely unexpected/config/infra faults (missing canonicalizer, transient resolver/network error, any non-library exception) → **Warning**. Otherwise a single hostile client drives unbounded Warnings and *masks* the real misconfiguration the logging was meant to surface — the observability goal defeats itself.
- **Watch for overloaded exception types at the classification seam.** `MultibaseCodec.Decode` wraps a malformed `proofValue` (attacker input) into the **same** `ZcapLd.Core.Exceptions.CryptographicException` used for the missing-canonicalizer **config** fault. Can't split by type at the catch — so retype the input-level case at its source (`DecodeProofValue` rethrows as `CapabilityValidationException`) instead of trying to disambiguate downstream.
- **A regression test that names a specific catch must assert that catch's specific log message.** The first revocation test asserted only "some Warning with an exception" — which the *outer* catch also satisfied, so it would have passed even if the inner catch were deleted. Assert on the attributing message (`"IsRevokerAuthorizedAsync failed closed…"`) to actually pin the inner behavior. Guard a severity seam in BOTH directions (one Debug test for expected input, one Warning test for an injected non-library fault).
- **Long-lived cumulative branches can ship non-compiling intermediate states.** PR #84 (#58–#64 stacked) had a real `CS0103` from a merge that moved a `capability.Id`-referencing log block into a helper scope that only had `chain`. CI/reviewers can't evaluate #64 in isolation. Prefer merging the lower issues and rebasing the top issue to a minimal delta before final review/merge.

## 2026-06-03 (later) — Plan-gate recurred a THIRD time; and "let the resolver self-provide" beats churning every fixture
- **Recurrence (3rd time):** On "update deps + make the adjustments" I created the branch (good) but then edited the csproj + a `using` + a field BEFORE presenting a plan. The user stopped me: "tell me what is the plan. you're supposed to ask for approval." **A direct imperative to implement ("make the adjustments") is STILL a planning trigger when the task is ≥3 steps / architectural** — the instruction to *do it* is not the instruction to *skip the plan*. Pattern to internalize: branch-first and plan-approval are two separate gates; clearing the first does not clear the second. Read-only exploration before the plan is fine and expected; the moment an edit is a *mutation* of shippable files, stop and `EnterPlanMode` → plan file → `ExitPlanMode`.
- **Replacing a string heuristic with real resolution breaks fixtures built on fake identifiers.** Swapping `VerificationService`'s DID-string controller match for document resolution (`IVerificationRelationshipResolver`) made 36 tests fail — they used synthetic `did:key:z6MkRoot`-style DIDs that the *signing* backend accepts (keyed by registered private key) but a real `DidKeyMethod` cannot decode → `ControllerNotResolvable` → fail-closed. The fix was NOT to rewrite 36 tests to use real keys, nor to weaken the production default: it was to let the resolver that already knows a method's DIDs **also answer relationship authorization** — `VerificationService` selects `relationshipResolver ?? (didResolver as IVerificationRelationshipResolver) ?? default`. Then the test/example `InMemoryDidProvider` implements the interface with did:key-equivalent semantics and is picked up automatically; `DidKeyResolver` self-provides the real document path. One helper change per backend instead of per-test churn, and a more cohesive design (the capability travels with the resolver that owns the DIDs).
- **When you change runtime behavior, RUN the app, not just the tests.** The unit suite went green but the console `examples/` (separate `InMemoryDidProvider`, synthetic DIDs, 2-arg `VerificationService`) printed `Valid: False` for happy-path flows until its provider got the same interface. `dotnet test` passing ≠ the product works; for a behavior change, execute the example/app and read the actual output (and remember `--no-build` runs the STALE binary — rebuild before trusting it).

## 2026-06-05 — A "negative" regression test must be proven by ABLATION, and watch for upstream gates that mask the guard
- **PR #88 review (🔴):** the test for the #68 key-type/suite guard (`VerifyInvocation_WhenResolvedKeyTypeMismatchesSuite_ReturnsFalse`) passed **with the guard removed** — full suite stayed green. Same family as the 2026-06-03 catch-message lesson ("would pass even if the guarded code were deleted"), but a new mechanism: the test asserted `.BeFalse()` and got false **from an unrelated upstream gate**, not the guard under test.
- **Mechanism — fallback resolver masked the guard.** The test's `WrongKeyTypeResolver` implemented only `IDidResolver`, not `IVerificationRelationshipResolver`. So `VerificationService` fell back to a real `did:key` relationship resolver (`?? CreateDefaultRelationshipResolver()`), which can't decode the test's **synthetic** `did:key:z6Mk…` controller → verification failed at **step 6 (controller authorization)**, a gate *before/independent of* the thing under test. The honest verifier passed only because `InMemoryDidProvider` *does* implement the relationship interface — so the real difference between the two verifiers was the relationship resolver, not the key type. Fix: the test double must forward **every** authorization gate to the honest backend so the **single** factor under test is the only difference (here, `WrongKeyTypeResolver` now delegates `IsAuthorizedForRelationshipAsync` to its inner provider).
- **Rule — prove negative tests by ablation.** A test asserting "X is rejected" is worthless until you've confirmed it **fails when the guard is removed**. Temporarily neuter the guard (e.g. `KeyTypeMatches => true`), run the test, watch it go red, then restore. If it stays green, it's testing the wrong gate. Do this for every fail-closed/deny test, not just the happy path.
- **Rule — isolate by holding all other gates passing.** In a multi-gate verifier (suite-binding → signature → controller auth → caveats → revocation → replay), a deny-test only isolates gate N if gates 1..N-1 and N+1.. all PASS for the crafted input. A test double that accidentally trips an *earlier* gate gives a false green. Pair every deny-test with a sanity assertion that the same input verifies true under the honest setup.
- **Rule — guard duplicated across paths needs a test PER path.** The #68 guard existed in both `VerifySingleDelegationProofAsync` and `VerifyInvocationSignatureAsync`; only the invocation copy had (a broken) test. Extracting a shared `KeyTypeMatches` helper gives one source of truth, but still add one regression test per entry path (invocation + delegation) so neither call site can silently lose its guard.
