# Issue #149 — remove unsafe typed caveats and align the supported v0.4 profile

Scope approved by the user: all recommendations in the preceding assessment; no
compatibility requirement for existing capabilities. Branch: `149-remove-typed-caveats`.

## Implementation plan

- [x] Remove typed caveat models, registry/converter, processor, remote handler and DI APIs.
  Reject any capability `caveat` field (including null/empty and extension data) on
  signing, validation and verification, including embedded ancestors. Preserve
  cryptographic suites and canonicalization. Use `MalformedCapability` for rejection.
- [x] Add `VerificationPolicy.AllowTargetAttenuation`, default false. Share the
  lexical `/`, `?`, `&` narrowing rule and traversal guard with creation. Add an
  optional target to delegation creation; choosing a narrower creation target is
  explicit, while verifier acceptance remains independently configured.
- [x] Migrate callers/tests/examples to the new APIs; retain security regressions
  for forbidden caveats rather than retaining unsupported caveat semantics.
- [x] Add adversarial coverage across signing, single-proof/chain verification,
  both invocation APIs, embedded parents, and exact/attenuated target policies.
- [x] Fix interop dependency pins; retain the existing 12 assertions and add
  cross-stack caveat rejection and delegation/invocation target-policy matrices.
- [x] Update README, package README, architecture, requirements, revocation,
  compatibility and release documentation; correct #144's overstated integrity
  claim in repository documentation and explain #112's superseded caveat scope.
  Explain application enforcement and distributed revocation limits. v0.3 already
  contains the caveat-removal note; v0.4 does not mandate changing cryptosuites.
- [x] Obtain one independent adversarial review, address findings, run solution
  tests, examples, interop harness and Release packaging. Prove key negative
  regressions fail when the corresponding guard is removed.

## Review and validation

- Full solution tests: **420 Core + 8 ASP.NET passed**, zero failures/skips.
- Live JS interoperability: **12/12 baseline + 109/109 profile checks passed**.
  Existing baseline expectations and supported proof golden vectors are unchanged.
- Console example: both invocation formats, two-hop path/query attenuation, exact-only
  rejection, signed ancestor revocation and descendant rejection all succeed.
- Release packaging: Core and ASP.NET **5.0.0** packages and symbol packages built.
- Independent adversarial review: one concrete revocation profile-consistency finding
  reproduced (unsupported embedded capabilities in request body/proof). Fixed by
  guarding all four representations before signature/store processing. Regression
  cases assert the store remains untouched and clean signed revocations still work.
  Reviewer rebuilt and passed all **33 profile tests**; no blocking finding remains.
- Ablation: disabling the profile guard fails all **7/7** selected legacy parameter /
  revocation regressions. Disabling the exact-target gate fails **3/9** target cases.
  Guards were restored in `finally` blocks before the final full-suite run.
- Traversal tests cover cycles, JSON depth and total work bounds. HTTP tests prove
  null/empty/typed caveats survive deserialization and are rejected without recording.
- `git diff --check` passes. Solution build succeeds. Existing XML-documentation
  warnings and SQLitePCLRaw.lib.e_sqlite3 2.1.11 NU1903 warnings remain outside scope.
- User's pre-existing `.claude/settings.json` change is untouched. No publication,
  external issue comment, commit or PR was performed.

No legacy capability migration mode is provided: there are no production systems
requiring it. The #144 correction and #112 supersession are documented in the
repository compatibility report; this work does not claim full v0.4 conformance.
