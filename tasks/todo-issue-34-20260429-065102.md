# Issue #34 — JCS signing payload wrapper bug

GitHub: https://github.com/moisesja/zcap-dotnet/issues/34

## Problem
`ProofSigningPayloadBuilder.CanonicalizeCapabilityJcs` and `CanonicalizeInvocationJcs` build a non-standard wrapped payload `{ capability: {...}, proof: {...} }` before JCS canonicalization. W3C Verifiable Credentials Data Integrity (and every other library, including `zcap-py`) signs over a **flat** payload — the document's own top-level fields plus a `proof` field with `proofValue` removed. Result: zcap-dotnet signatures are unverifiable by any other implementation, and vice versa.

Also affected:
- Hand-picked proof field whitelist in JCS path will silently drop new proof fields (nonce, domain, id, challenge).
- Same whitelist risk in RDFC-1.0 path's `proofOptions` dictionary (lines 145-153, 173-184).
- `DateTime` fractional-digit precision drift (.NET produces 7 digits, Python produces 6) — separate cross-stack issue but in the same hot path.

## Review

### What changed
- [src/ZcapLd.Core/Cryptography/ProofSigningPayloadBuilder.cs](src/ZcapLd.Core/Cryptography/ProofSigningPayloadBuilder.cs) — `CanonicalizeCapabilityJcs` and `CanonicalizeInvocationJcs` now produce the W3C Data Integrity flat payload (document's top-level fields plus a `proof` field carrying the proof minus `proofValue`) by round-tripping through `System.Text.Json` so model attributes (`[JsonPropertyName]`, `[JsonIgnore(WhenWritingNull)]`, `[JsonConverter]`) drive the shape. RDFC-1.0 proof-options dicts now copy from the `Proof` object minus `proofValue` instead of hand-picking five fields, fixing the same forward-compat hazard.
- [src/ZcapLd.Core/Cryptography/IsoUtcMicrosecondDateTimeConverter.cs](src/ZcapLd.Core/Cryptography/IsoUtcMicrosecondDateTimeConverter.cs) — new converter factory emitting `yyyy-MM-ddTHH:mm:ss.ffffffZ`. Wired onto [`Proof.Created`](src/ZcapLd.Core/Models/Proof.cs) and [`Capability.Expires`](src/ZcapLd.Core/Models/Capability.cs) via `[JsonConverter]`. Local-kind DateTimes are normalized to UTC.
- [tests/ZcapLd.Core.Tests/Compliance/CrossLanguageJcsInteropTests.cs](tests/ZcapLd.Core.Tests/Compliance/CrossLanguageJcsInteropTests.cs) — 5 known-answer tests pinning JCS canonical bytes for capability + invocation, the 6-digit DateTime format on both `Proof.Created` and `Capability.Expires`, and Local→UTC normalization.

### Test results
- 287 tests pass (282 pre-existing + 5 new). 0 failures.
- The known-answer test asserts the exact canonical JSON string for a fixed capability + proof. Any future drift in shape, key set, or DateTime format trips this test with an actionable diff.

### Breaking change
Any signature produced by zcap-dotnet ≤1.1.0 over the old wrapped `{capability, proof}` shape (or with 7-digit DateTime precision) will not verify against this version. Per issue #34's "Backward compatibility" section, no real-world cross-language deployments depend on the broken shape (since none could have worked), so a hard cutover is the right call. Single-stack consumers re-sign anything they had cached.
