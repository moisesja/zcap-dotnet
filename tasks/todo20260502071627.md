## Review

Conclusion: using https://w3c-ccg.github.io/zcap-spec/ as the sole source of truth, the codebase is much closer than earlier branches and the current compliance test matrix passes, but it is not yet fully compliant with the current W3C CCG ZCAP-LD v0.3 draft.

Validation:

- `dotnet test tests/ZcapLd.Core.Tests/ZcapLd.Core.Tests.csproj --filter FullyQualifiedName~Compliance` passed: 47 tests.
- `dotnet test ZcapLd.sln` passed: 308 tests.
- `dotnet build ZcapLd.sln` passed with 7 nullable warnings in `examples/ZcapLd.Examples/Program.cs`.

Blocking compliance gaps found:

- Controller cardinality is incomplete: the spec permits `controller` as a string or array of strings for root and delegated zcaps, but `Capability.Controller` is a single `string` and authorization compares against only that one value.
- Proof cardinality is incomplete: the spec permits delegated `proof` as an object or array of objects with at least one capability delegation proof, but `Capability.Proof` is a single `Proof`.
- Root validation is too permissive: `CreateRootCapabilityAsync` emits the correct root shape, but `ValidateCapabilityAsync` does not reject root `allowedAction`, `caveat`, or extension fields even though the spec says root zcaps must not have any other fields.
- Capability chain construction embeds the root zcap for first-level delegations, but the draft says the root zcap is included using its ID, by reference only, and only the parent delegated zcap is fully embedded. For a parent delegated capability, `BuildCapabilityChain` also extracts IDs from object entries in the parent's chain, then adds the parent ID and embeds the parent; if the parent chain contains an embedded root object this can duplicate the root ID in child proof chains.
- Delegated DI invocations are not represented in the spec-required shape: the draft says a delegated DI invocation's `capability` property must express the full delegated zcap. The current `Invocation.Capability` is a `string`, `SigningService.SignInvocationAsync` copies that string into `Proof.Capability`, and `VerificationService.VerifyInvocationAsync` requires it to equal `capability.Id`.

Non-blocking / partial areas:

- The current implementation supports Data Integrity proof generation and verification for Ed25519/P-256 through registered suites, but not every example suite/field shape from the draft (`jws`, `signatureValue`, RSA).
- Revocation support exists and checks revoked IDs during chain verification, but `VerificationService.RevokeCapabilityAsync` only records an ID/revoker and does not itself prove the revoker is a chain controller.
- The compliance matrix is useful, but several tests assert generated happy-path shapes rather than spec rejection behavior for malformed or alternative valid shapes.
